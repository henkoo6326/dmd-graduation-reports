작품 분석 A

O.K — 차세대 교정 업무 시스템

팀 콩밥 · 2025 PIVOT-TIME 15번 · 디자이너 4 + 프로그래머 2 (6인) · 웹 빌드 약 7~8주
8.75
종합 / 10
무엇을 만들었나. 교도관을 위한 스마트 통합 업무 시스템. 태블릿(통합 업무) + 스마트워치(긴급 대응) + 키오스크(공용 대시보드) 3개 디바이스 생태계에 하이브리드 AI 어시스턴트 "OK-E"를 얹은 구조.

기획 · 문제정의

8.5
  • 법령→정책→통계 3중 근거 스택. 「교도관직무규칙」 제34조 → 1차 교정기본계획(2021~2025)의 스마트 교정·NFC 시범사업 → 공공부문 AI 도입률 95% 목표. 동기들이 설문 90명, 뉴스 인용 3건 수준일 때 솔루션을 "정부 로드맵의 다음 단계"로 자리매김.
  • 주제 블루오션 선점. 20팀 중 유일한 교정행정 주제. 접근이 어려운 폐쇄 조직을 택해 희소성 확보.
  • Device 챕터를 문제와 솔루션 사이에 배치해 "문제 정리 → 그래서 앱" 비약을 차단. 기기별 채택 근거를 각각 정당화.
  • 공공 프로젝트의 현실 감각. KRDS 준거, 푸터 면책 고지, AI 활용 고지 — 학생 컨셉이 아닌 "납품 가능한 제안서"의 태도.

시각디자인 · 브랜딩

9.0
  • 조형 근거를 주제에서 도출. 범정부 디자인 시스템 KRDS 확장형 적용을 명시, 국문 Pretendard GOV + 영문 Gotham, 자간 -5% / 행간 150%까지 수치 고정. 다크모드를 "선명한 모드"로 재명명해 가시성 관점으로 리프레이밍.
  • 위험도 컬러 시맨틱. 블루 #0015FF=경미/확인, 오렌지 #FF4D00=긴급 규칙이 워치 알림·키오스크 배지·UI 레전드까지 3개 디바이스를 동일하게 관통.
  • 스타일 키워드 3종(홀로그래픽·글래스모피즘·네오퓨처리즘)을 실물로 증명. 투명 스크린 키오스크, 파티클 락스크린, 3D 아이소메트릭 안양교도소 맵으로 키워드→구현 추적 가능.
  • 더미 데이터까지 통제한 세계관. 페르소나 '김현겸 교도관'이 락스크린("김현겸 교도관님(잠금)")과 인수인계 모달 칩("인계자: 김현겸")에 재등장.

UX · 서비스 설계

8.5
  • '앱'이 아니라 '시스템'을 설계. 상황 × 기기 특성 매트릭스로 기능을 배분하고 핵심/플러스/부 위계까지 명시.
  • 실동작 AI 챗봇. "OK-E를 체험해보세요" 섹션이 railway 백엔드를 실제 호출 — 20팀 중 유일하게 심사위원이 직접 질문할 수 있는 동작하는 프로토타입.
  • 엣지케이스의 UI 환원. SOS 입력을 "5대 교정 사고 유형" 선택으로 분류 체계화, "양손이 자유롭지 않은 상황"을 무전 인터랙션 근거로 명시, AI 인력 자동 재배치 에스컬레이션 정의.
  • 스펙 문서 수준의 기능 밀도. 수용자 프로파일 하나를 영상 7개로 분해, 인수인계의 데이터 연동 사양(AI 감시 로그·CCTV·NFC)까지 명시.

전달 · 프레젠테이션

9.0
  • 6챕터 매거진형 구조. "01 시스템 전략"~"06 OK-E" 넘버링 카드 + 8개 라우트 — 동기 대부분이 단일 세로 스크롤일 때 심사위원이 원하는 지점으로 즉시 점프 가능.
  • 영상 29개 자동재생. webm 26 + mp4 3의 실동작 UI 영상을 전 페이지 자동재생 배치 — '읽는 설명'을 '보는 시연'으로 대체.
  • 내러티브 일관성. 근거 카드 3장 → 페르소나 4인 호버 페인포인트 → 그 페르소나가 락스크린 UI에 재등장 → 비전 카피로 마무리.

감점 요인

1차 리서치(현장 인터뷰) 부재 · 통계 출처 미표기 · 감시/인권·프라이버시 쟁점 완전 침묵 · NFC 실패/네트워크 단절/AI 오탐 등 실패 모드 미정의 · 페르소나 4인 대비 태스크 플로우 커버리지 불균형 · MVP/확장 우선순위 부재 · 에셋 위생 실패(fuckdong.png 파일명, 번들 평문 시스템 프롬프트) · 라이브 챗봇 폴백 없음 · 629KB 단일 번들 + 영상 29개 자동재생 성능 리스크 · 로고 설명이 감성 서술 수준.

작품 분석 B

E.S.C. — Emergency System Center

팀 삐용삐용 · 2024 BE 4번 · 디자이너 3 + 개발자 3 (6인) · 웹은 개발자 1인이 약 3주에 완성 (정적 HTML + jQuery + Three.js)
8.25
종합 / 10
무엇을 만들었나. '응급실 뺑뺑이' 문제를 겨냥해 구급대원·병원·시민 3주체를 하나로 연결하는 통합 응급 서비스. 구급대원 앱(체크리스트·지도) + 병원용(알림·AI 병원정보) + 시민 앱(신고 매뉴얼) + 차량 거치 iPad 내비게이션.

기획 · 문제정의

7.5
  • 사회적 합의가 끝난 문제의 선점. 도입부가 "구급대원들의 업무 증가, 원인은?" 질문과 키워드 칩 '응급실 뺑뺑이'로 시작 — 심사위원이 문제의 존재를 별도로 설득받을 필요가 없는 주제. 같은 해 21팀 다수가 라이프스타일 주제였다.
  • 3주체 이해관계자 정의가 서비스 아키텍처 그 자체. 페르소나 3인(구급대원=골목 진입·인계 대기 / 병원=구두 소통 / 시민=위치 불안)이 그대로 3색 컬러 시스템과 앱 3종 구조로 이어진다.

시각디자인 · 브랜딩

8.5
  • 컬러가 정보 아키텍처로 작동. Neon Green #E0FD48(구급대원) / Red Cross #FF3E3E(병원) / Safe Blue #0177FF(시민) + 다크 베이스 — "각 주체를 명확히 구분하기 위해 세 가지 컬러를 사용"을 명문화. 색만 따라가도 "지금 누구의 화면인가"가 읽힌다.
  • 로고의 브랜드 자산화. '달리는 사람' 픽토그램을 그리드 드로잉 애니메이션 → Three.js 3D 로고 3종 → 스플래시 3색 변주로 전개 — 아이덴티티의 설계 과정 자체를 시연.
  • 전시장 레벨 검증. 코랄 핑크·청록·핫핑크가 지배적인 썸네일 그리드에서 21팀 중 가장 강한 다크+네온 대비로 물리적 차별화. 컨셉 문장("긴박한 상황에서도 가시성을 잃지 않는 스타일")이 썸네일까지 이탈 없음.

UX · 서비스 설계

8.5
  • 멀티스테이크홀더 정보구조. 사용자별 분리 설계 + 차량 iPad 내비게이션. 동기 대부분이 단일 사용자군 앱 1개를 제안한 것과 스코프가 다르다.
  • 엣지케이스의 화면 환원. '좁은 골목길' 페인포인트가 경로 옵션 3종(최소시간 15분 / 골목없는 경로 21분 / 최적 25분)으로, 이동 신고자 문제가 "최초 신고 지점으로부터 547m + 경로 재안내"로, 의식 없는 환자가 체크리스트 분기로 번역됨.

전달 · 프레젠테이션

8.5
  • 3색이 그 자체로 내비게이션 역할을 하는 원페이지 내러티브. 화면 녹화 영상 15개 + 어노테이션.
  • 크로스디바이스 일치 시나리오 데이터. 2024.10.04 기준 동일 인물(홍길동/김철수/이서현)·동일 시각의 가상 데이터가 화면을 관통 — '실제로 돌아가는 서비스'라는 인상.
  • 포커스 인터랙션과 출처 투명성. 호버한 카드만 남기고 블러 처리, SOURCE 버튼으로 에셋 출처 공개.

감점 요인

정량·법령 근거 전무 · 기존 제도(중앙응급의료센터 종합상황판)와의 차별성 논증 생략 · 혈액형/복용약/임신여부 등 민감 개인정보의 법적 근거 무검토 · 병원 매칭 거부 시 재매칭 플로우 부재 · 문제정의 2개 vs 솔루션 3개 비대칭 · 문제정의 문단의 오탈자("일일히", "연략해야한다") · 최종 시연 영상을 최하단 클릭 재생으로 배치 · 히어로 카피("구급대원을 위한 앱")와 본문(3주체 플랫폼)의 불일치 · 학교·학과·전시 맥락 언급 0건.

검증을 통과한 수상 요인 24개를 관통하는 하나의 공식이 있다.

The Formula

희소한 공공 문제 선점 → 이해관계자 정의가 컬러·IA·UI 데이터까지 관통하는 시스템 설계 → 조형 결정마다 논증 부착 → 동작하는 증거로 시연

01

사회적 합의가 끝난 공공 문제를 선점한다

O.K는 20팀 중 유일한 교정행정, E.S.C.는 21팀 중 유일한 생명 직결 공공 시스템 위기. 동기 다수가 라이프스타일·소비자 앱일 때 "심사위원이 심각성을 이미 아는" 문제를 골라 주제 선정 단계에서 체급을 갈랐다.

실행 지침 — 주제 확정 전 동기들의 주제 분포를 먼저 조사하고, 지금 뉴스에 나오는 공공·시스템 문제 중 아무도 안 하는 것을 골라라.
02

이해관계자 정의가 구조적 뼈대가 된다

O.K의 페르소나 이름이 락스크린·모달 칩까지 재사용되고, E.S.C.의 3주체가 3색·앱 3종·3D 로고 3종에 1:1 대응. 리서치 챕터와 디자인 챕터가 같은 인물·같은 데이터로 채워진다.

실행 지침 — 페르소나를 문제 제기용 인용문으로 소비하고 끝내지 마라. 그 정의가 컬러 시스템·IA·UI 더미 데이터·목업 콘텐츠까지 내려가야 한다.
03

컬러가 정보를 운반한다

O.K는 블루=경미 / 오렌지=긴급의 위험도 시맨틱, E.S.C.는 주체 구분 신호. 두 해 공통의 출품작 표준 문법(키컬러 1색 + 단색 배경 목업)과 격이 다른 지점.

실행 지침 — 컬러에 역할(위험도 등급, 사용자 주체, 상태)을 배분하고 그 규칙이 모든 화면에서 깨지지 않음을 목업으로 증명하라. 단, 주체 축과 상태 축은 분리할 것.
04

조형 결정에 논증을 붙이고 실물 증거로 닫는다

O.K의 KRDS·Pretendard GOV·자간 -5%/행간 150% 수치 고정, E.S.C.의 컨셉 문장이 썸네일까지 무이탈. 무드보드와 실제 화면이 단절되면 선언은 감점 요인이 된다.

실행 지침 — "왜 이 서체, 왜 이 스타일인가"에 주제로부터 도출된 답을 붙이고, 키워드→실제 UI의 추적 가능성을 이미지로 남겨라.
05

구조적 약점

패턴 7의 "동작하는 증거"를 만들 개발자가 없다. 그러나 E.S.C.의 웹은 프레임워크 없는 정적 HTML + jQuery를 개발자 1인이 3주에 만든 물건이다 — 이 수준은 AI 코딩 도구로 충분히 도달 가능하고, 우리 팀은 이미 Claude Code로 쇼케이스 HTML을 만들어본 경험으로 이를 입증했다.

구조적 강점

디자이너 5명. O.K(디자이너 4), E.S.C.(디자이너 3)보다 조형 생산력이 크다. 두 작품의 핵심 설득 장치는 코드가 아니라 "영상 + 목업 품질 + 내러티브"였다 — 전부 디자이너의 무기다.

전략 A주제 선정 기준과 후보 방향

수상작 검증 요인에서 도출한 4가지 기준. 네 가지 모두 통과하는 주제를 골라라.

기준 1

심사위원이 이미 심각성을 아는, 뉴스에 나오는 공공·시스템 문제인가 — E.S.C.의 '응급실 뺑뺑이' 기준.

기준 2

법령·정부 계획·공식 통계로 근거 스택을 쌓을 수 있는가 — O.K의 직무규칙 제34조 → 교정기본계획 → AI 95% 기준.

기준 3

이해관계자가 2주체 이상이어서 시스템 설계(멀티 앱/멀티 디바이스)로 확장되는가.

기준 4

동기 팀들이 안 할 만큼 접근이 어렵거나 무거운가 — 주제 확정 전 반드시 동기들의 주제 분포를 먼저 조사할 것.

1

1인 가구 고독사 · 위기가구 발굴 시스템

사회보장급여법·복지 사각지대 발굴 시스템(행복e음)이라는 기존 제도가 있어 "왜 실패하는가" 논증 가능. 사회복지 공무원 / 이웃·신고자 / 당사자 3주체. 프라이버시 쟁점 1페이지까지 설계하면 O.K가 놓친 지점을 정면 돌파.

2

학대아동 조기 발견 · 신고 연계 시스템

아동복지법·아동학대처벌법 + 전담공무원/경찰/의료진/교사의 다자간 조율 문제. 접근 어려운 폐쇄 도메인이라는 점에서 O.K형 희소성.

3

전세사기 예방 · 피해자 대응 통합 플랫폼

전세사기특별법이라는 최신 법령, HUG·등기부 공공데이터, 임차인/공인중개사/보증기관 3주체. "지금 뉴스에 나오는" 시의성 최상.

4

산업재해 현장 안전 관제 시스템

중대재해처벌법 + 고용노동부 스마트 안전장비 보급 사업이 O.K의 "정부 로드맵의 다음 단계" 논법을 그대로 재현. 작업자 워치 / 관리자 태블릿 / 안전보건공단 대시보드의 멀티디바이스 구조가 자연스럽다.

재난 시 취약계층 이송 우선순위 시스템

AI 코딩으로 구현한다 — 가능 판정

  • 쇼케이스 사이트 — 챕터형 멀티페이지(O.K식) 또는 앵커 원페이지(E.S.C.식). GSAP 스크롤 인, 호버 블러 포커스, 드래그 캐러셀, 자동재생 영상, lazy-load까지 전부 가능. 이미 팀이 해본 영역.
  • Three.js 3D 로고/오브젝트 — 3D 모델링은 디자이너가 Blender/Spline로 만들고, 웹 탑재만 AI 코딩으로.
  • 소품 인터랙션 — 로고 그리드 드로잉 애니메이션, 타이포 모션, 페르소나 호버 스와프 전부 가능.
  • 라이브 AI 데모 1개 — O.K의 OK-E와 동급을 Claude API로 구현 가능. 단 O.K의 실패를 반복하지 말 것: 녹화 영상 자동 폴백 내장, 프롬프트는 서버 측 보관, 데모 범위는 1개 시나리오로 좁게.
  • 앱의 "동작" 증거 — 실코딩 앱 대신 Figma + ProtoPie 프로토타입을 화면 녹화한 영상을 자동재생 임베드. O.K의 영상 29개도 실기기 앱이 아니라 UI 영상이었다 — 심사위원이 보는 것은 영상이다.

포기한다 — 하지 않을 것

  • 네이티브 앱 / 실서비스 백엔드 / DB / 로그인 등 실제 소프트웨어 개발. 심사에 기여하지 않는다.
  • 복잡한 실시간 기능(지도 실연동, 푸시). 영상 시나리오로 대체.
  • 프레임워크 고집. 정적 HTML로도 E.S.C. 수준이 나온다. AI 도구가 잘 다루면 써도 무방하되, 629KB 단일 번들 같은 성능 함정을 피하도록 빌드 결과를 반드시 점검.

브랜딩 리드		1로고(그리드 근거→모션→변주 운용 체계), 컬러 시맨틱 시스템 설계(주체 축과 상태 축 분리), 디자인 토큰·서체 논증, 전시 썸네일·포스터
디자인 2·3
프로덕트 UI		2주체/디바이스별 UI 화면 전량, 세계관 더미 데이터 통제(페르소나 이름·날짜·장소를 전 화면 일관), 엣지케이스 화면(실패 모드·동의 화면 포함), Figma/ProtoPie 프로토타입
디자인 4
모션 · 영상		1기능별 UI 시연 영상 15개+ 제작(O.K식 기능 분해), 최종 시연 영상, 어노테이션, 히어로 영상
디자인 5
웹 · 3D — AI 코딩 담당		1Claude Code로 쇼케이스 사이트 구현, Three.js/Spline 3D 에셋 탑재, 라이브 데모 1개+폴백, 성능·에셋 위생 게이트
주 1회 전원 교차 점검. "리서치 챕터의 인물·수치가 디자인 챕터 화면에 그대로 있는가"(패턴 2), "무드보드 키워드가 실제 화면에 있는가"(패턴 4)를 체크리스트로 상호 검증.

전략 D산출물 체크리스트 — 수상작 수준 기준

쇼케이스 사이트

  • 챕터 넘버링 구조(O.K 6챕터) 또는 3색 내비게이션 원페이지(E.S.C.) — 3분 심사 점프 가능
  • 상단에 문제-솔루션-임팩트 요약 레이어 + 시연 영상 자동재생
  • 문제 근거 카드: 법령 조문 1 + 정부 계획 1 + 통계 3 (전부 기관·연도 각주)
  • 전문가 인터뷰 1건 표기 ("현직 OO N인 인터뷰, 2026.OO")
  • 기존 제도 실패 분석 1페이지 + 윤리/법 검토 1페이지 + KPI 정의
  • 디바이스/매체 선택 근거 챕터 (문제와 솔루션 사이)
  • MVP vs 확장 단계 로드맵
  • 푸터: 학교·학과·캡스톤 맥락, 면책, AI 활용 고지, 에셋 출처, 팀 크레딧

프로토타입 · 데모

  • 기능별 UI 시연 영상 15개 이상 (핵심 기능 1개는 O.K처럼 5~7편 분해)
  • 실동작 데모 1개(AI 챗봇 또는 인터랙티브 시뮬레이션) + 녹화 영상 자동 폴백
  • 크로스디바이스에서 일치하는 가상 시나리오 데이터 (동일 인물·동일 시각)
  • 엣지케이스 화면 3종 이상: 실패 모드 1, 예외 분기 1, 동의/권한 화면 1

브랜딩 · 비주얼

  • 컬러 시맨틱 규칙 명문화 + 전 화면 무이탈 증명 (주체 축/상태 축 분리)
  • 로고 운용 체계 (그리드 근거→모션→3D 또는 변주)
  • 스타일 키워드→실제 화면 매핑 이미지
  • 자체 제작 그래픽 모티프 최소 1축 (외부 에셋 의존 상쇄)
  • 전시 썸네일: 동기 그리드에서 물리적으로 차별되는 대비 전략 (E.S.C. 다크+네온 사례)

위생 · 품질

  • 제3자 전수 교열 (특히 문제정의 문단)
  • 파일명·번들 문자열 전수 점검
  • 첫 3초 로딩 테스트, 영상 lazy-load
  • 히어로 첫 문장 = 시스템 구조 일치 확인

전략 E일정 프레임

참고 실측치: O.K 웹 빌드 7~8주(83+커밋), E.S.C. 웹 3주(개발자 1인). 전시는 11월 넷째 주. 1학기 리서치 병행 ~ 2학기 완성 기준의 역산 프레임.
